ModChecker 0.1.0
===============

Статический сканер Minecraft-модов с консольным режимом и окном Swing.
Он читает jar и .jar.sample как архив и НЕ запускает код мода.


Запуск
------
Без аргументов открывается окно:
java -jar modchecker.jar

С одним аргументом работает консольный режим:
java -jar modchecker.jar <папка mods, один .jar или .jar.sample>

Например:
java -jar build\libs\modchecker.jar build\testmods
java -jar build\libs\modchecker.jar C:\образцы\мод.jar.sample

Файлы .jar.sample проверяются так же, как .jar. Это удобно для образцов,
которые нельзя случайно запустить двойным кликом.


Окно программы
--------------
- В поле пути можно выбрать папку с модами, один .jar или .jar.sample.
- Кнопки "Папка..." и "Файл .jar/.sample..." открывают обычный выбор файлов.
- Папку, .jar или .jar.sample можно перетащить мышкой прямо в окно.
- Если существует %APPDATA%\.minecraft\mods, этот путь подставляется сразу.
- Кнопка "Проверить" запускает проверку в фоне, окно не замирает.
- На полосе прогресса видно "мод 5 из 20".
- Таблица: Мод | Вердикт | Очки | Modrinth | CurseForge.
- Строки окрашены: подозрительные - красноватые, неизвестные - жёлтые,
  доверенные - голубоватые, ОК - зелёные, ошибки - серые.
- Нажатие на заголовок сортирует таблицу. По умолчанию сверху идут
  ПОДОЗРИТЕЛЬНО, затем НЕИЗВЕСТНО, ДОВЕРЕН (вручную), ОК и ОШИБКА.
- Нажатие на строку показывает SHA-1, все находки с очками и местом,
  ссылки и статусы сайтов в нижней панели.
- Внизу видны итоги: ОК / ДОВЕРЕН / НЕИЗВЕСТНО / ПОДОЗРИТЕЛЬНО / ОШИБКА.
- Для выбранной строки есть кнопки "Доверять этому файлу" (с подтверждением)
  и "Убрать из доверенных".
- "Сохранить отчёт" пишет полный отчёт в UTF-8 .txt в том же формате,
  что и консольный режим.


Что проверяется
---------------
- строковые константы в .class;
- текст в .json, .txt, .properties, .cfg;
- вложенные .jar и .jar.sample до двух уровней;
- известные строки (Discord/Telegram, данные аккаунтов и браузера, кошельки,
  Pastebin, Fractureiser); правило Cookies проверяется только в .class,
  чтобы не ловить имена методов в refmap .json;
- простая маскировка строк: Base64, hex, переворот, XOR, StringBuilder, char[];
- заметки: до 10 Base64-строк, которые раскрываются в обычный текст
  (очков не дают, нужны для ручной проверки);
- отдельные опасные вызовы: загрузка кода, Runtime.exec/ProcessBuilder,
  сетевые подключения, обращение к APPDATA/user.home;
- если Runtime.exec/ProcessBuilder находится в том же методе, где есть строка
  explorer, xdg-open, open или rundll32/url.dll, это считается открытием
  папки/ссылки и даёт 1 очко вместо 3; также срабатывает случай, когда
  команда лежит в соседнем методе класса, а вызов - в open*;
- связки КРАЖА и ЗАГРУЗЧИК считаются только внутри основного кода или
  одного и того же вложенного jar; в отчёте показаны места обеих частей;
- сбор ID железа: OSHI, MAC-адрес, wmic/реестр Windows (правила 22 и 23);
- наличие исполняемых файлов внутри jar;
- SHA-1 на Modrinth и отпечаток CurseForge;
- ручной список доверенных SHA-1 в trusted_hashes.txt.


Ключ CurseForge
---------------
Используется файл с именем curseforge_key.txt.
В файле должен быть только сам ключ, без кавычек.

В окне есть поле ключа, кнопка "Показать", кнопка "Проверить ключ",
галочка "Запомнить ключ" и кнопка "Удалить ключ".
Если поле ключа пустое, проверка CurseForge пропускается.
Ключ не выводится в консоль, отчёт или сообщения об ошибках.

Если поставить "Запомнить ключ", GUI сохранит его сюда:
Windows: %APPDATA%\modchecker\curseforge_key.txt
Остальные системы: ~/.modchecker/curseforge_key.txt

При следующем запуске GUI сам загрузит этот ключ.
Старый способ тоже работает: если сохранённого ключа нет, GUI ищет
curseforge_key.txt в папке запуска, затем в ~/.modchecker.
Консольный режим по-прежнему ищет ключ по этим старым правилам.

НЕ кладите ключ в build\libs: команда gradlew clean удаляет папку build
вместе с ключом. Ключ в корне проекта, в ~/.modchecker или в
%APPDATA%\modchecker пересборку переживает.

Если вы копируете modchecker.jar в другую папку и запускаете оттуда,
папка запуска - это папка с jar. Тогда ключ можно положить рядом с jar
(но не в build\libs при разработке).


Доверенные хеши
---------------
Ручной список доверенных файлов читается из двух мест:
- trusted_hashes.txt рядом с проверяемым jar;
- Windows: %APPDATA%\modchecker\trusted_hashes.txt
- Остальные системы: ~/.modchecker/trusted_hashes.txt

Формат строки:
SHA-1  комментарий

Пустые строки и строки, начинающиеся с #, пропускаются. Если SHA-1 мода
найден в списке, вердикт становится ДОВЕРЕН (вручную) независимо от очков.
Все находки всё равно показываются в отчёте, а очки не меняются.

Кнопка "Доверять этому файлу" спрашивает подтверждение и добавляет хеш
в общий файл %APPDATA%\modchecker\trusted_hashes.txt.
Кнопка "Убрать из доверенных" удаляет хеш из общего файла и из файла
рядом с выбранным модом.

Файл trusted_hashes.txt с личными хешами исключён в .gitignore и не должен
попадать в репозиторий.


Что программа НЕ ловит
----------------------
Это статический эвристический сканер, а не антивирус и не песочница.
Он не запускает мод и не видит, что мод делает во время игры.

- Не выполняет мод и не наблюдает его поведение.
- Не делает полную декомпиляцию и не восстанавливает весь код.
- Не строит полный граф потока данных и не эмулирует произвольный байткод.
- Не расшифровывает AES/RC4/кастомные шифры и сложную обфускацию.
- Не ловит строки, которые появляются только во время выполнения.
- Не ловит полезную нагрузку, скачанную позже, и код, загруженный с сервера.
- Не анализирует содержимое .exe/.dll/.bat/.cmd/.ps1/.vbs/.scr:
  правило 17 только отмечает сам факт наличия такого файла.
- Не ищет .so/.dylib отдельным правилом и не анализирует native-код.
- Не проверяет содержимое скриптов и не знает, что они делают.
- Не сканирует как текст .yml/.yaml/.toml/.xml/.lang/.nbt/.dat и другие форматы.
- Не смотрит вложенные jar глубже двух уровней.
- Не рекурсивно проверяет произвольные .zip и ресурсы, кроме вложенных
  .jar и .jar.sample.
- Не ловит рефлексию, MethodHandle, invokedynamic и кастомные загрузчики классов,
  если в байткоде нет известных вызовов.
- Не ловит вредоносные действия через обычные API (например, удаление файлов),
  если для них нет отдельной сигнатуры.
- Не ловит неизвестные домены, кастомные протоколы, DNS-туннели и стеганографию.
- Не гарантирует обнаружение любого сбора HWID: правило 22 ищет известные
  вызовы OSHI/NetworkInterface и строки Windows-команд, а не все способы.
- Не проверяет сетевой трафик и не видит, куда реально уходят данные.
- Не проверяет подписи jar, сертификаты и личность автора.
- Не определяет зависимости и их версии, не проверяет известные уязвимости (CVE)
  в библиотеках. Shaded-код просматривается только теми же строками и вызовами.
- Не находит логические бомбы, атаки по времени/условию и социальную инженерию.
- Не проверяет страницы сайтов вручную: только SHA-1/отпечаток файла.
- Совпадение с сайтом означает только то, что файл совпал с официальной
  страницей, а не то, что он безопасен.
- Возможны ложные срабатывания и пропуски.
- "ПОДОЗРИТЕЛЬНО" - не приговор. "НЕИЗВЕСТНО" - не гарантия безопасности.


Что означает вердикт
--------------------
- ПОДОЗРИТЕЛЬНО - 10 и больше очков.
- ДОВЕРЕН (вручную) - SHA-1 есть в trusted_hashes.txt; это ручное решение
  пользователя, а не подтверждение сайта. Находки всё равно показываются.
- ОК - меньше 10 очков и файл подтверждён на Modrinth или CurseForge.
- НЕИЗВЕСТНО - меньше 10 очков, но подтверждения сайта нет.
- ОШИБКА - файл не читается как jar.


Подтверждение с сайта = файл тот же, что на официальной странице.
ПОДОЗРИТЕЛЬНО = проверь сам, это не приговор.
